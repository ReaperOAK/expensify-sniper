Each line cost at least one failed run. Read them as constraints, not trivia.

- The signed-in test account is BRAND NEW and EMPTY: no contacts, workspaces, expenses or reports, only its own self-DM. Any step that assumes existing data fails. A run died on `wait_for text=j.doe` searching for a contact that never existed.
- Expensify is React Native Web: every CSS class name is generated and unstable. Only testID (`data-testid`), aria-label, role and visible text are usable selectors. Never use `css=` on a class.
- `id` is NOT `data-testid`. A run died on `wait_for testid=composer` because `CONST.COMPOSER.NATIVE_ID = 'composer'` is an `id` attribute; the real testID is `CONST.COMPOSER.TEST_ID.REPORT_ACTION_COMPOSE = 'reportActionCompose'`. Read the attribute off the live DOM rather than inferring it from a constant's name.
- An element can exist and still be unclickable. If `count()` is 1 but `click()` times out on actionability, look for an overlay before doubting the selector — that is how the onboarding modal wasted a whole run.
- Creating a chat with a fabricated email address DOES work (search the address, the invite row appears, click it). Creating one with a bare name does not.
- The dev server proxies `/api` to production, so real backend behaviour applies: a change that needs a server-side flag will not reproduce locally.
- Steps are replayed TWICE (before the fix and after), so they must be re-runnable. The first pass mutates the app. Never assert on first-visit-only UI — `text=Say hello!` (the empty-chat placeholder) broke a run because the first pass had already populated that chat. Put `{{RUNID}}` in every name/email you invent so each pass creates fresh data.
- The test account is on a PUBLIC domain (gmail.com). `areEmailsFromSamePrivateDomain` (`src/libs/LoginUtils.ts:84-86`) returns false whenever either side is public, so this account has NO short-mention namespace at all. Any issue about short mentions, private-domain grouping, or same-domain user lists is UNREPRODUCIBLE with it — do not "reproduce" such a bug, you are only observing specified behaviour.
- Before trusting a reproduction, check whether the assertion was written from the same assumption as the diagnosis. A repro authored to confirm a theory is not independent evidence of it. Look for a checked-in spec or a named test that already defines the behaviour as intended.
- Multi-user issues ARE reproducible. `as_user("b")` creates and signs in a brand-new Expensify account in its own browser context. Every account is a `+tag` alias of one mailbox (`x+sniper@gmail.com` -> `x+sniperb@gmail.com`), so logins are automatic. Do not skip an issue for needing a second account.
- A first-ever login for a NEW alias is slow: Expensify creates the account before mailing the code, which overran a 150s poll. The code arrived just after the poller gave up, which looks exactly like "no code was sent". CODE_TIMEOUT_S is now 300.
- Gmail preserves the `+tag` in `Delivered-To`, so magic codes MUST be filtered by recipient when more than one account is in play — otherwise user B's login silently consumes user A's code.
- Both refutations so far killed the REPRODUCTION, not the theory: #96348 asserted what a checked-in spec defines as correct; #96352 clicked the header title (`DisplayNamesWithToolTip`) rather than the "From" link and blamed the element it never touched. Before implementing, confirm the repro exercised the exact element/branch being blamed, and that a CONTROL element does not behave the same way.
- IMAP polling must REUSE one connection. Reconnecting every 5s meant ~60 Gmail logins per wait, each SELECT+SEARCHing a 37k-message mailbox; Gmail throttled it and the poller died with "The read operation timed out", which reads exactly like "the code never arrived". Raising the timeout made it worse by doubling the login count.
- The dev server's port opens BEFORE rsbuild finishes compiling; after checking out a different commit that is a full rebuild. Waiting only for the socket then sleeping makes the first navigation hang and the run dies with a bare "Page.goto: Timeout", which reads as a broken repro rather than a cold server. Poll for an actual HTTP 200 before driving the browser.
- Playwright locators are STRICT by default: an ambiguous selector raises "strict mode violation ... resolved to N elements" and kills the run. `label=Create expense` matched twice and ended a 17-of-18 repro. `_locator` now appends `.first` on every branch; prefer a unique testID anyway.
- A bare `.first` can match a HIDDEN copy, so `wait_for` passes and the next `click` times out. But do NOT fix that with `filter(visible=True)` in the shared locator: visibility is evaluated at match time, so a not-yet-rendered element matches nothing and `wait_for` times out on an empty locator — that regressed a run from 18 steps to 8. Keep `.first` for waiting; the click verb retries against a visible match on failure.
- Prefer `testid=` over `label=` for menu items and buttons. The FAB menu exposes `FABMenu-CreateExpense`, `FABMenu-CreateReport`, `FABMenu-TrackDistance`, `FABMenu-StartChat`, `FABMenu-NewWorkspace` — all unique and clickable. `label=Create expense` matches more than one node and the first matches are not clickable; it burned several runs. Read the real `data-testid` off the live DOM with browser_evaluate (the accessibility snapshot does NOT include testids).
